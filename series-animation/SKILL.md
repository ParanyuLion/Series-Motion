# Series animation (Thai, code-drawn, Remotion)

This folder (`series-animation/` at the repository root) is the master copy of the skill. `.claude/skills/series-animation/SKILL.md` is only a pointer so Claude Code discovers it; edit the files here.

The user is making a short-video series for Instagram Reels and TikTok. Every picture is drawn by code (SVG in Remotion), not generated by AI video models, and one AI narrator speaks Thai. The first series is a survival drama on a deserted island (7 people, 5 parts). Part 1 exists and has been iterated on many times; this skill keeps everything learned so far.

Always reply to the user in Thai. They are a Thai creator and judge the Thai wording, tone and voice better than anyone.

## Where things live

- Project: `E:\Coding\animation\Remotion` (Remotion 4, TypeScript, Python helpers). Git repo root is `E:\Coding\animation`, remote `https://github.com/ParanyuLion/Series-Motion.git`, branch `main`. The user asked for the work to be committed and pushed to `main`; commit after each meaningful change with the attribution line the session gives.
- Story and decisions: `docs/superpowers/specs/2026-10-21-island-survival-series-design.md`, the approved script `docs/superpowers/specs/part1-script-draft.md`, the plan `docs/superpowers/plans/2026-10-21-island-part1.md`.
- Part 1 code: `Remotion/src/island/` and `Remotion/scripts/island/`. The finished pilot (a boy and a firefly) lives in `Remotion/src/` and `Remotion/scripts/`; leave it alone.

## Workflow for each new part (follow in order)

1. **Read the references** that apply: `references/series-bible.md` for the story, cast, tone and voice decisions, `references/visual-style.md` before touching pictures, `references/pipeline.md` before running anything, `references/feedback-log.md` to see what the user already corrected (so the same mistake is not repeated).
2. **Write the script first, as text, and get the user's approval before building anything.** Thai, first person "ผม" (the hero นที narrates), about 400 Thai characters of narration per minute (measured: ~7.5 characters per second at the chosen voice speed, excluding spaces). Include the title that appears on screen, the picture plan, and which lines are spoken by another character. The user reads Thai well; ask them to react to tone and word choice. Then build only after "ok".
3. **Build one part at a time**, from the previous part's code. Timing always comes from the narration audio through `src/island/manifest.json`; never hard-code frame numbers (see the pipeline reference).
4. **Check what you can and say what you cannot.** Render stills at the key frames and look at them; run the verify script; measure loudness. You cannot watch the video play or hear the audio, so say so plainly and ask the user to watch and listen. Do not claim the pacing or the pronunciation is good.
5. **Hand over** with the file path, what changed, the things you could not check, and the next question. Keep it short. Then wait for feedback.

## How to handle the user's feedback (this is the point of the skill)

When the user gives a correction or a preference, do the work, then **record it in the same turn** so it is never forgotten:

- Add a dated line to `references/feedback-log.md` (what they said, what was changed, which files).
- If it is a lasting rule rather than a one-off (for example "always do X", a style choice, a thing to avoid), also add it to the right section of `references/visual-style.md`, `references/series-bible.md` or `references/pipeline.md`, and to "Standing preferences" below if it applies to everything.
- Commit the updated skill files together with the code change.

If a new preference contradicts an older one, update the old line instead of keeping both, and tell the user.

## Standing preferences (apply to every part)

- **Talk Thai, show results, keep messages short.** Lead with what was done and where the file is. Admit gaps (not watched, not heard) in one line.
- **Approve text before building.** Script and names are agreed in chat first. One part at a time.
- **Do not re-voice for visual changes.** Narration audio is generated once and cached. Picture and animation changes only need a re-render; changing the script text for a line means a new Gemini request for that line. Never spend Gemini quota on something that only changes pictures.
- **Do not re-render the picture for audio-only changes** (louder or quieter music, voice speed). Use `scripts/remix.py` (copies the video stream, rebuilds the audio in seconds).
- **No jarring cuts.** The user disliked abrupt scene transitions. Prefer one continuous world with a moving camera; use cuts only deliberately (aerial view, face-on close-up) with a short fade.
- **The picture must never feel empty or static.** The user asked for more zoom, several camera angles, better light and shadow, and a fuller background. Keep adding depth: foreground, midground, background, light shafts, fog, small props.
- **Face-on close-up when a character smiles or has a key emotional beat.** The side-on rig is the default; cut to the front-facing close-up (`FaceFront`) at those beats.
- **Nothing may float.** Any decoration must be attached to something or to the edge of the frame (a floating fern at the left edge was reported as a bug).
- **Music must stay under the narration.** The user asked for quieter music once; the bed plays at volume 0.5 and ducks under speech.
- **Safe area for the platforms.** Burned-in Thai subtitles, 60 px left, 160 px right, 340 px bottom margins; keep figures above the subtitle band.
- **Deaths are implied, never graphic** (platform rules and the bleak style).
- **Secrets:** the Gemini key lives only in `Remotion/.env` (git-ignored). Never print it, quote it, or commit it.
- **Credit and originality.** The pilot idea came from another creator's Thai adaptation; for the series, write original stories, not copies.

## When you are stuck

- Gemini quota errors: read `references/pipeline.md` (quota table and fallbacks) before trying anything; do not burn requests blindly.
- A visual idea is bigger than the 2D rig can do (rotating characters, true 3D): say so, offer the 2D alternatives listed in `references/visual-style.md`, and let the user choose.
